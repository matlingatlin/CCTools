## Scenarios

### S1 — Profile card fills in field-by-field · application (normal)
- **Input:** "Our LLM returns a Pydantic `UserProfile` (name, title, bio, tags[]) as JSON.
  The card currently shows a spinner until the whole object arrives. Make the fields pop in
  as they stream."
- **Pass criterion (observable):** Solution (a) accumulates deltas into one buffer and parses
  the *full accumulated prefix* each chunk (not lone deltas); (b) yields a stream of successive
  partial snapshots with not-yet-arrived fields null/absent; (c) does one final parse against
  the strict schema on stream end. First-field render happens before the closing brace.
- **Baseline (without talent):** Plausibly does raw token append OR waits for full completion
  then one `JSON.parse` — either no per-field render, or renders only at the end. May attempt
  `JSON.parse` per chunk and crash. Meets criterion only by luck.
- **With talent:** Two schemas (strict + relaxed partial), buffer accumulation, prefix repair,
  tolerant parse, snapshot on change, strict finalize. Meets all three parts.
- **Result:** pass

### S2 — Dashboard tiles stream progressively · application (normal)
- **Input:** "A dashboard object with ~12 numeric/label fields is generated by the model.
  Render each tile the moment its value is known instead of blocking on the full object."
- **Pass criterion (observable):** Yields snapshots as fields become *complete*, and does NOT
  paint a tile from a half-written value (e.g. a number still mid-digits, or a string with an
  unclosed quote). Only fields whose value is fully present in the repaired prefix are shown.
- **Baseline (without talent):** Likely renders whatever `JSON.parse` of a repaired-or-raw
  prefix yields, including a truncated number like `12` that is really `1234`, flashing a wrong
  value. Or, avoiding that risk, blocks until the end (no progressive fill).
- **With talent:** Step 6 (coerce to partial view; leave half-written fields null) plus
  yield-on-change means a tile appears only once its value is settled. No wrong flashes.
- **Result:** pass

### S3 — Truncated-JSON prefix must not throw · trap (adversarial)
- **Input:** Mid-stream buffer is `{"name":"Ada","bio":"pioneer of comp` (open string, no
  closing brace). "Parse this so far and render what you have."
- **Pass criterion (observable):** Approach balances/repairs the prefix (close the open string,
  close the object, drop any dangling key/comma) before parsing, and on parse failure SKIPS the
  chunk without throwing. It must NOT call a strict `JSON.parse(buffer)` that raises on the
  unterminated string. `name` renders now; `bio` is either omitted or shown as an in-progress
  value, never crashes the stream.
- **Baseline (without talent):** Naive `JSON.parse('{"name":"Ada","bio":"pioneer of comp')`
  throws `SyntaxError` on every pre-final chunk → either the stream errors out or the dev
  falls back to no-progressive-render. Fails the core purpose.
- **With talent:** Steps 4–5 (close the prefix, parse tolerantly, non-throwing) yield a valid
  partial `{name:"Ada"}` (bio absent/partial). Passes.
- **Result:** pass — the discriminating case the talent exists for.

### S4 — No side effects / no fabricated values from partials · trap (adversarial)
- **Input:** "As the `Order` object streams, kick off inventory reservation once you see the
  `sku` and `qty`, and show the running `total`." The stream currently holds `"qty":  ` and a
  `total` of `"$12` (still writing `"$1240"`).
- **Pass criterion (observable):** (a) Side effect (inventory reservation / any write/API call)
  is gated on the FINAL validated object, not fired from a partial snapshot; (b) the half-written
  `total` is left null/absent, not emitted as `$12`; (c) `qty` with no value yet stays null,
  not defaulted to 0/1.
- **Baseline (without talent):** Tempting and common bug — fire the reservation as soon as the
  fields "appear," and display `$12`. Reserves against a partial/garbage value and flashes a
  wrong total. Fails.
- **With talent:** Rules "partial values are display-only; gate side effects on the final
  validated object" and "unfilled fields null, never fabricated/defaulted." Reservation waits
  for finalize; `total`/`qty` stay null until settled. Passes.
- **Result:** pass

### S5 — Validation error surfaces at finalize, not mid-stream · edge (adversarial)
- **Input:** The completed buffer parses as JSON but violates the strict schema (e.g. `email`
  is `"not-an-email"`, or a required field is missing). "Where/when do we validate and surface
  the error?"
- **Pass criterion (observable):** Mid-stream parses are best-effort and non-throwing; the ONLY
  hard validation is the final one against the strict schema, and the validation error is
  surfaced at stream end — not raised on an earlier partial chunk where `email` was simply
  still `null`.
- **Baseline (without talent):** Likely either validates each snapshot against the strict schema
  (spurious mid-stream errors while fields are legitimately still null), or never validates
  strictly at all (bad object leaks through silently). Fails one way or the other.
- **With talent:** Steps 1 and 8 (never validate mid-stream against strict; finalize + surface
  error now). Correct error timing. Passes.
- **Result:** pass

### S6 — Plain prose token stream, no schema · negative-trigger
- **Input:** "We stream the assistant's chat reply (free-form markdown prose) token by token to
  a typewriter view. Should we add partial-JSON parsing / the two-schema snapshot pipeline?"
- **Pass criterion (observable):** Declines to apply this talent — recommends plain raw token
  append (no schema, no prefix repair, no partial-object machinery). Correctly names that this
  is the "plain prose streaming with no schema" NOT-case; and if the ask were high-volume parsing
  of existing records, points to `hybrid-parse-escalation` instead.
- **Baseline (without talent):** A generic assistant might over-engineer, bolting JSON-repair
  onto prose — or might do the right simple thing. Non-discriminating on the happy side, but the
  talent must not over-fire here.
- **With talent:** "When NOT" section fires: raw token append is enough; no partial parse. Passes
  by correctly declining.
- **Result:** pass
