## Q1

Three separate bugs, all at the stage seams, and they compound:

**1. `revenue/transform.py:15` — the 100x scale bug (this is the APAC number).**
`extract.py` deliberately normalises amounts to *minor units* (integer cents) — see the docstring at `extract.py:3-5` and `_to_minor_units` at `extract.py:12-20`. `transform.to_usd` (line 15) does `record["amount"] * rate` on that cents-integer and stores the result as `amount_usd` without ever dividing back by 100. Every downstream total is 100x too large in dollar terms, and `report.py` prints it straight with `$%.2f` (`report.py:24`).
Proof: `41,339,000.00 / 100 = 413,390.00` — that's Finance's "APAC did about $0.4M" almost exactly. Ran it: `python3 -m revenue.run feed.csv` reproduces `$41339000.00` for APAC.

**2. `revenue/transform.py:3-7` and `:20` — GBP silently dropped (this is the North America number).**
`FX_TO_USD` only has USD/EUR/JPY. `feed.csv` rows N-3003, N-3004, N-3005 are North America in GBP (214000.00 + 186500.00 + 97300.25 = 497,800.25 GBP — by far the largest chunk of NA's revenue). `to_usd` returns `None` for GBP (line 13-14), and `aggregate`'s `if r is not None` (line 20) quietly excludes them — no warning, no log, nothing. NA's reported total is built from only its two USD rows ($111,750.75), which is why it computes as the *smallest* region even though Finance says it should dwarf the others.

**3. `revenue/report.py:16` — ranking is not actually ranking anything.**
`rank()` sorts on `r.get("total", 0)`, but `transform.aggregate` emits the key `total_usd` (`transform.py:25`), never `total`. So every row's sort key is the same default `0`, and Python's stable sort just preserves `aggregate`'s dict-insertion order — which is first-appearance order per region in `feed.csv` (APAC, then EMEA, then North America). "Top region: APAC" / "North America last" is an artifact of feed row order, not revenue. `report._amount()` (lines 6-11) *does* correctly read `total_usd` for display, so the printed dollar figures are internally consistent with bug #1 while the ordering is silently wrong — that's a nasty combination to debug from output alone.

Net effect matches the complaint exactly: APAC's true total ≈ $413K (bug 1 explains the inflated $41.3M), and NA's true total is understated because ~$630K+ of GBP revenue never entered the sum (bug 2), and even once those are fixed the "Top region" line still won't reorder correctly until bug 3 is fixed too.

## Q2

What this suite cannot catch, structurally:

- **Cross-stage contract breaks.** Every stage is tested against hand-built fixtures, never against a real prior stage's output. `tests/test_report.py:6-7`'s `row()` helper builds `{"region_code": ..., "total": ...}` — using the key `"total"`, which happens to be the *same wrong key* `report.rank()` looks for. That's exactly why bug #3 above (real key is `total_usd`) never surfaces: the test's fixture and the buggy code agree with each other, not with reality. There is no test anywhere that pipes `extract.parse_rows` → `transform.aggregate` → `report.rank`/`render` together.
- **Unit/scale contracts.** `tests/test_transform.py` and `tests/test_transform_fx.py` build records with `rec(100.0, ...)` — dollar-scale floats — never the integer-cents values `extract.parse_rows` actually produces. So the 100x scale bug (bug #1) is invisible to the entire transform suite; it's testing arithmetic that's correct in isolation but on inputs that don't match the real contract.
- **Silent data loss / completeness.** `test_unpriceable_currency_returns_none` (`test_transform_fx.py:49-50`) confirms GBP → `None` is the *intended* per-record behavior, but nothing checks what that does at the `aggregate()` level — no test asserts a region's total reflects all its rows, or that dropped rows are counted/logged/surfaced anywhere. A silently-zeroed chunk of revenue for a real region is exactly what's invisible here.
- **Coverage of the FX table against the actual feed.** No test cross-checks that every currency code appearing in `feed.csv` (or any real feed) has an entry in `FX_TO_USD`. GBP showing up in the feed but not the rate table is never flagged.
- **No test of `run.py`/`main()`**, i.e. nothing exercises the wired-together job at all, and no test loads `feed.csv` (the actual data file the nightly job runs against) and checks the output against a known-correct number.
- **No sanity/plausibility check on magnitudes** (e.g., "region total shouldn't jump 100x between runs," or bounds-checking rendered totals) that would have flagged the scale bug as an anomaly even without knowing the root cause.

In short: 34 green unit tests, zero integration tests, and two of the fixture helpers happen to encode the same wrong assumptions as the bugs they're near.

## Q3

No. `test_transform_fx.py` is thorough for what it targets — rate-table sanity (`RateTable` class), conversion arithmetic including the specific March regression, zero/negative amounts, linearity, and confirming GBP is (by design) unpriceable — but that's a narrow slice of the pipeline, and it's not where two of this incident's three bugs live:

- It doesn't touch the scale bug (bug #1): its `rec()` fixtures use dollar-scale floats (`rec(1000.0, "EUR")`), never the integer-minor-units contract `extract.py` actually hands to `transform.py`, so it can't see the missing `/100`.
- It doesn't touch the ranking bug (bug #3): that's in `report.py`, a different module entirely.
- It stops at "GBP returns `None`" and never follows that through `aggregate()` to see a region's total silently missing a currency's worth of revenue (bug #2's actual mechanism) — the test only proves the per-record function does what it was told to, not that the aggregate output is complete.

So this suite would catch a repeat of the exact March incident (stale/wrong EUR rate), but it gave false confidence for this incident: it's the newest, most-scrutinized suite in the repo and it's green, while the real faults are a unit mismatch and a field-name mismatch at the seams between `extract`→`transform` and `transform`→`report` that no suite — this one included — exercises end to end.
