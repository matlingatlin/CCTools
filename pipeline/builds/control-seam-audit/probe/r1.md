## Q1

Three separate bugs, all at the *seams* between the three stages, not inside any one
stage's own logic. Ran the pipeline and reproduced the reported numbers exactly, then
recomputed by hand:

**Bug A — `revenue/transform.py:15`, missing the minor-units divide-back.**
`extract.py` normalises every amount to integer *cents* (its own docstring, lines 3-4,
and `_to_minor_units`, line 12-20, say so explicitly). `transform.to_usd()` then does:

    return {**record, "amount_usd": record["amount"] * rate}

`record["amount"]` is still cents, and the result is never divided by 100, so
`amount_usd` is 100x too large in dollar terms. $41,339,000.00 / 100 = $413,390 — which
is almost exactly Finance's "about $0.4M" for APAC. This is the main source of the
inflated headline number.

**Bug B — `revenue/transform.py:3-7`, GBP is missing from `FX_TO_USD`.**
Three of North America's six feed rows (`N-3003/4/5`) are in GBP (~£497,800 combined —
more than half of NA's raw volume). `to_usd()` returns `None` for any unpriced
currency (line 13-14) and `aggregate()` silently drops those rows (line 20: "rows we
cannot price are not part of the total" — no warning, no count, nothing). So over half
of NA's real revenue never enters the total. Once you fix Bug A and reprice only the
priceable rows, NA comes out to $111,750.75 — dead last, exactly as last night's run
showed — but the moment GBP is priced at all (even a rough ~1.27), NA's true total
jumps to roughly $740K, comfortably above APAC's $413K and EMEA's $183K. This is why
Finance sees NA as biggest "by a wide margin" and we don't: we're quietly throwing away
its GBP orders.

**Bug C — `revenue/report.py:16`, `rank()` sorts on the wrong key.**
`transform.aggregate()` emits rows shaped `{"region_code": ..., "total_usd": ...}`
(`transform.py:25`). But `report.rank()` does:

    return sorted(rows, key=lambda r: r.get("total", 0), reverse=True)

There is no `"total"` key on real rows — only `"total_usd"` — so every row's sort key
is `0` and `sorted` (being stable) just returns the rows in whatever order
`aggregate()`'s dict produced them, i.e. first-appearance order in the feed. APAC rows
are first in `feed.csv`, so APAC "wins" by file position, not revenue. Notice
`report._amount()` two lines above (line 9-11) correctly checks `"total_usd"` first —
`rank()` and `_amount()` disagree with each other about the schema inside the same
file. So even after fixing A and B, the ranking itself is currently accidental, not
computed.

Net: the reported ranking and magnitude are both artifacts of these three bugs
compounding, and none of them are inside a single stage's "business logic" — they're
all in the undocumented/untested contract at the extract→transform and
transform→report boundaries.

## Q2

What the current 34 tests (`tests/test_extract.py`, `test_transform.py`,
`test_transform_fx.py`, `test_report.py`) verify is real, but every one of them
exercises a stage in isolation with hand-built fixtures — never the actual data shape
one stage hands the next. Concretely, it cannot catch:

- **Cross-stage schema/unit drift.** `test_transform.py`'s `rec()` helper (line 6-8)
  and `test_transform_fx.py`'s `rec()` helper (line 9-11) both pass amounts like
  `100.0` / `1000.0` directly into `transform.to_usd()`, as if they were already
  dollars. Real input from `extract.parse_rows()` is integer cents. Nothing ever pipes
  `extract`'s actual output into `transform` and checks the result, so Bug A (the
  missing /100) is invisible to this suite by construction.
- **The report.py key mismatch.** `test_report.py`'s `row()` helper (line 6-7) builds
  `{"region_code": ..., "total": ...}` — matching what `rank()` expects, not what
  `transform.aggregate()` actually produces (`"total_usd"`). The test suite for
  `report.py` was written against a schema `transform.py` doesn't emit, so it can't
  catch Bug C.
- **Silent data loss from unsupported currencies.** `test_unpriceable_currency_returns_none`
  (both transform suites) only checks that a *single record* returns `None`. Nothing
  checks what happens at the `aggregate()`/region-total level when a currency is
  missing from the rate table — there's no assertion that this is logged, counted, or
  bounded, so a whole currency silently vanishing from a region's total (Bug B) is
  unguarded.
- **No integration/golden-output test.** There is no `test_run.py` and no test that
  calls `revenue.run.main()` or chains `extract → transform → report` end to end
  against `feed.csv` (or any fixture file) with a known expected answer. All three
  bugs above only became visible when the whole pipeline was actually run against real
  data — which is exactly what none of the 34 tests do.
- **Realistic/adversarial `feed.csv` shapes.** `test_extract.py` covers dot vs comma
  decimals and one clean 3-row CSV, but not: missing/blank fields, unknown region
  strings, duplicate `order_id`s, an empty file, extra columns, or amounts with
  currency symbols.
- **Floating-point drift at scale.** `aggregate()` accumulates into a Python `float`
  (`transform.py:23-24`); no test sums enough rows, or large enough magnitudes, to
  expose accumulation error.

## Q3

No. `test_transform_fx.py` is thorough for the one thing it was scoped to — the FX
*rate table* and the conversion *arithmetic* (rate values in plausible bands, USD
identity, linearity, sign handling, zero handling) — and it would genuinely catch a
repeat of the March stale-rate incident. But of the three bugs found in Q1, it catches
zero of them:

- It never touches `report.py`, so it cannot see the `rank()` vs `"total_usd"` key
  mismatch (Bug C) — that's simply out of its file's scope.
- Its own `rec()` fixture (line 9-11) feeds `to_usd()` plain dollar-scale floats, the
  same as the older `test_transform.py`, so it inherits the same blind spot to the
  minor-units contract from `extract.py` — it cannot see Bug A.
- `test_unpriceable_currency_returns_none` (line 49-50) tests GBP specifically and
  asserts `to_usd()` returns `None` — which is *correct* given the current table, so
  it passes happily whether or not GBP is a currency you actually need to support. It
  has no test asserting `FX_TO_USD` covers every currency that appears in production
  feeds, so a real region silently losing revenue to an unpriced currency (Bug B) is
  invisible to it.

It's a good regression guard for "did someone edit a rate to the wrong number," which
was the March failure mode. It is not, and was never designed to be, a guard against
unit mismatches or missing-currency data loss — both of which are exactly what's
biting us now. We are not covered; we need an integration test against `feed.csv` (or
an equivalent fixture) with a hand-computed expected total per region, plus a test
that `FX_TO_USD` is a superset of the currencies appearing in any feed we run.
