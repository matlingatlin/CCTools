## T1

Setup: 12 outputs, 6 from arm `with_skill`, 6 from arm `baseline`. One grader scores all 12.
The 12 are really 6 *items* (same question answered twice), so they must be graded as 6 paired
comparisons, not 12 loose scores — otherwise the grader can drift between questions.

Three files. The grader sees only the first.

**1. `grading_prompt.md` — what the grader receives (arms relabelled)**

```
You are grading pairs of answers. For each of the 6 items below you will see the same
question answered twice, as "Response P" and "Response Q".

You do not know, and must not try to infer, which system produced P or Q. P and Q are
assigned independently for EACH item: the fact that P was better on item 1 tells you
nothing about item 2. Do not carry any impression across items. Do not attempt to
identify a system by writing style, length, formatting, hedging, or self-reference.
If you think you recognise a system, ignore that belief and grade the text in front of you.

For each item, in order, output exactly one line:

  item=<id>  winner=<P|Q|TIE>  margin=<1|2|3>  reason=<= 25 words>

margin: 1 = barely, 2 = clear, 3 = decisive. TIE requires margin=0.

Criteria, applied in this order:
  1. Correctness — are the claims true and the reasoning sound?
  2. Responsiveness — does it answer the question actually asked, in full?
  3. Actionability — could the reader act on it without asking a follow-up?
  4. Concision — length is only a tiebreaker; longer is not better.

Do NOT output an overall summary, an overall winner, or any statement of the form
"P was consistently stronger". Per-item lines only. Aggregation is done elsewhere.

--- ITEM 1 ---
Question: <q1>
Response P:
<...>
Response Q:
<...>

--- ITEM 2 ---
...
```

**2. `key.json` — held back from the grader, written before grading, never edited after**

Labels are re-randomised per item (coin flip per item), so the mapping is not constant:

```json
{
  "created_utc": "2026-08-30T00:00:00Z",
  "arms": ["with_skill", "baseline"],
  "randomisation": "per_item_independent",
  "seed": 20260830,
  "items": {
    "q1": {"P": "with_skill", "Q": "baseline"},
    "q2": {"P": "baseline",   "Q": "with_skill"},
    "q3": {"P": "baseline",   "Q": "with_skill"},
    "q4": {"P": "with_skill", "Q": "baseline"},
    "q5": {"P": "baseline",   "Q": "with_skill"},
    "q6": {"P": "with_skill", "Q": "baseline"}
  }
}
```

Generated, not hand-written, so the assignment is not mine to nudge:

```python
# make_key.py  -- run once; writes key.json and the blinded prompt bundle
import json, random
items = ["q1","q2","q3","q4","q5","q6"]
rng = random.Random(20260830)
key = {}
for i in items:
    first_is_new = rng.random() < 0.5
    key[i] = {"P": "with_skill" if first_is_new else "baseline",
              "Q": "baseline"   if first_is_new else "with_skill"}
json.dump({"created_utc":"2026-08-30T00:00:00Z",
           "arms":["with_skill","baseline"],
           "randomisation":"per_item_independent",
           "seed":20260830,"items":key},
          open("key.json","w"), indent=2)
```

Filenames in the bundle handed to the grader are `item_q3_P.txt` / `item_q3_Q.txt` — no
`new/`, `old/`, `v2/`, branch names, or timestamps, and the outputs are stripped of any
trailing "generated with…" lines that would leak the arm.

**3. `rulings.txt` — the grader's raw output, stored verbatim, unblinded only by joining to `key.json`.**

**What the grader is told about the relabelling — stated explicitly:**
The grader is told that (a) the two responses come from two different systems, (b) the P/Q
labels are randomised **independently for every item**, so P is not a system, and (c) it must
not attempt to identify the systems and must not emit an aggregate. It is **not** told which
arm exists, that one arm is "new" or "improved", the hypothesis being tested, how many items
favour either side, or that any prior result exists. It never sees `key.json`, and it is not
told the seed. One grader, one pass, all 12 outputs, same prompt and same model settings for
every item — that is what makes the 6 rulings comparable to each other.

## T2

I can't write that up as the result, and the summary as delivered has to be discarded rather
than re-worded.

The labels were re-randomised per item (`randomisation: per_item_independent` in `key.json`).
So "answer A was consistently stronger across all five questions" is not a statement about
either arm. "A" denotes a different system on different questions; a consistent win for A is
consistent only with respect to a label that moved. Under our key, an across-the-board A win
would unblind to a *split* — roughly alternating arms — not a sweep. Reading it as a win for
the new skill silently assumes a fixed mapping we deliberately did not use.

Two further problems with the summary itself: the grader was instructed not to produce an
aggregate, and it produced one — so this output is off-contract and its per-item discipline is
in question. And it says five questions; the run has six items. That discrepancy has to be
resolved before anything is scored: either an item was dropped or the grader lost one.

What I did instead: went back to the per-item rulings and computed the score from them.

```
# rulings.txt (verbatim from the grader)     # joined to key.json
item=q1 winner=P margin=2   -> with_skill
item=q2 winner=P margin=1   -> baseline
item=q3 winner=P margin=2   -> baseline
item=q4 winner=P margin=1   -> with_skill
item=q5 winner=P margin=3   -> with_skill
item=q6 <missing>           -> unscored
```

```python
import json
key = json.load(open("key.json"))["items"]
tally = {"with_skill":0,"baseline":0,"tie":0}
for line in open("rulings.txt"):
    f = dict(kv.split("=",1) for kv in line.split() if "=" in kv)
    if f["winner"] == "TIE": tally["tie"] += 1; continue
    tally[key[f["item"]][f["winner"]]] += 1
print(tally)
```

**Result as it stands: with_skill 3, baseline 2, ties 0, unscored 1 (q6 missing).**

Write-up: on 5 of 6 items scored, the new skill won 3 and lost 2 — a 3–2 split on n=5, which is
what a coin flip looks like. This does not support a claim that either arm is stronger; with 6
paired items the smallest result that would clear a two-sided sign test at p<0.05 is 6–0, and we
do not have it. The honest conclusion is **no measurable difference at this sample size**, with
q6 still to be graded and the grader's aggregate discarded as an artefact of the blinding.

## T3

The un-blinding step is `join(rulings, key) -> per-arm tally`. A test that only checks it runs,
or that it returns *a* verdict, passes just as happily when the mapping is inverted — which is
the one failure mode that silently flips the sign of the whole experiment. So the load-bearing
control is: **feed it a key with the arms swapped and assert the verdict comes back opposite.**

```python
# test_unblind.py
import copy, pytest
from unblind import tally_arms   # the real un-blinding function

RULINGS = [
    {"item":"q1","winner":"P"},
    {"item":"q2","winner":"P"},
    {"item":"q3","winner":"Q"},
    {"item":"q4","winner":"TIE"},
]
KEY = {
    "q1":{"P":"with_skill","Q":"baseline"},
    "q2":{"P":"baseline","Q":"with_skill"},
    "q3":{"P":"baseline","Q":"with_skill"},
    "q4":{"P":"with_skill","Q":"baseline"},
}

def swapped(key):
    return {i:{"P":m["Q"],"Q":m["P"]} for i,m in key.items()}

def test_known_fixture_maps_correctly():
    # hand-computed: q1->with_skill, q2->baseline, q3->with_skill, q4->tie
    assert tally_arms(RULINGS, KEY) == {"with_skill":2,"baseline":1,"tie":1}

def test_swapped_key_produces_the_OPPOSITE_verdict():
    """The control. Inverting the key must invert the arm tally, not merely
    return some tally. If this passes with an identical result, the un-blinding
    step is ignoring the key and the experiment is unmeasured."""
    base = tally_arms(RULINGS, KEY)
    flip = tally_arms(RULINGS, swapped(KEY))
    assert flip["with_skill"] == base["baseline"]
    assert flip["baseline"]   == base["with_skill"]
    assert flip["tie"]        == base["tie"]          # ties are label-invariant
    assert flip != base, "swapping the key changed nothing -- key is not being read"

def test_partial_swap_moves_exactly_the_swapped_items():
    """Guards the weaker bug: key read, but per-item mapping applied globally."""
    k = copy.deepcopy(KEY)
    k["q1"] = {"P":"baseline","Q":"with_skill"}       # flip q1 only
    out = tally_arms(RULINGS, k)
    assert out == {"with_skill":1,"baseline":2,"tie":1}

def test_asymmetric_fixture_so_a_sign_flip_cannot_hide():
    """A 2-2 fixture is invariant under swapping; such a fixture would let an
    inverted mapping pass. This one is deliberately lopsided."""
    r = [{"item":i,"winner":"P"} for i in ["q1","q2","q3","q4"]]
    base, flip = tally_arms(r, KEY), tally_arms(r, swapped(KEY))
    assert base["with_skill"] != base["baseline"]     # fixture is not balanced
    assert flip["with_skill"] == base["baseline"]

def test_missing_item_raises_rather_than_defaulting():
    with pytest.raises(KeyError):
        tally_arms(RULINGS + [{"item":"q9","winner":"P"}], KEY)

def test_key_is_read_only_after_grading():
    """key.json's mtime must predate rulings.txt's -- the key cannot have been
    written or edited once the rulings were visible."""
    import os
    assert os.path.getmtime("key.json") < os.path.getmtime("rulings.txt")
```

The second test is the one that matters: it asserts a *sign flip*, so an un-blinding step that
hardcodes P=with_skill, or that never opens the key at all, fails. The fourth exists because the
control is vacuous on a balanced fixture — a 2–2 result is its own mirror image — so the fixture
is deliberately lopsided. Run these in CI on the same commit that produces any published tally;
a result whose un-blinding step is untested is not a result.
