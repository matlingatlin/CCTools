## Q1

Twelve tickets, two versions, both output sets saved. Here is the setup I would run.

**Preparation (before any judging)**
1. Build a manifest, one row per ticket per version: `item_id` (t01..t12), `variant` (old|new), `output_path`.
2. For each of the 12 tickets, emit a *pair* record with the two outputs placed in a random order, drawn per item (not one order for the whole set). Record the mapping in a key file that the judge never sees:
   `pair_id, item_id, slot_A_variant, slot_B_variant, seed`.
3. Strip anything that identifies a version from the outputs themselves before they go to the judge: version headers, prompt echoes, model/version strings, run IDs, timestamps, filenames, differing boilerplate, trailing "generated by ..." lines. Version identity leaks through formatting far more often than people expect — if one variant always uses bullets and the other always prose, note it as a residual leak rather than pretending it is blinded.
4. Keep the key file out of the judging directory entirely.

**Judge prompt (use as-is)**

> You are scoring two candidate summaries of the same customer support ticket. You do not know how either was produced, and you must not speculate.
>
> TICKET:
> {ticket_text}
>
> SUMMARY A:
> {slot_a}
>
> SUMMARY B:
> {slot_b}
>
> Score each summary independently on a 1-5 scale for each criterion. 1 = fails badly, 3 = acceptable, 5 = could not be meaningfully improved.
> - **Faithfulness**: every claim is supported by the ticket; no invented facts, names, dates, amounts, or promises.
> - **Coverage**: the customer's actual problem, what they already tried, and what they are asking for are all present.
> - **Actionability**: an agent reading only the summary knows what to do next.
> - **Concision**: no filler, no restatement of the ticket, no padding.
>
> Then answer: which summary is better overall — A, B, or TIE? TIE is a real answer; use it when the difference would not change what an agent does.
>
> Output strict JSON and nothing else:
> {"a":{"faithfulness":n,"coverage":n,"actionability":n,"concision":n},"b":{...},"winner":"A"|"B"|"TIE","reason":"<= 40 words citing specific text from the summaries"}
>
> Judge only what is written. Do not reward length, formatting, or confident tone.

**Run protocol**
- Run every pair twice: once as presented, once with the two slots swapped (A/B position counterbalanced). That gives 24 judgements over 12 items and lets you measure position bias directly.
- Independent scoring first; the pairwise winner is a separate field, not derived from the totals.
- Only after all 24 judgements are written to disk, join on the key file and un-blind.

**Tally and read-out**
- Per-variant mean per criterion, plus win/loss/tie counts on the pairwise field.
- **Position-bias check**: how often did the judge pick slot A regardless of variant? If slot A wins materially more than half of all judgements, the numbers are contaminated and the criterion scores are the safer read.
- **Consistency check**: how often did the two orderings of the same item disagree? Every flip is an item where the judge had no real preference; count flips as ties, and if flips are a large share of the set, the honest answer is "no detectable difference at n=12".
- Report a direction and a caveat, not a verdict: 12 items is a smoke test. Say how many items would be needed to call a small difference, and say plainly when the result is inside the noise.

I would also hand-read three or four items myself against the judge's calls before believing the aggregate.

## Q2

This script is a re-identification step: it takes anonymised labels and restores which version produced each answer. Its failure modes are silent and they corrupt the result rather than crashing, so the tests have to be about correctness of the mapping and about not leaking, not just "does it run".

Cover:

**Correctness of the mapping**
- Round-trip: blind a known set, map it back, assert every answer lands on the version it actually came from. This is the central test and it should use a fixture where the truth is known independently of the script.
- Per-item randomisation is respected: a fixture where item 1 has (A=old, B=new) and item 2 has (A=new, B=old) must not be collapsed into one global rule. A script that hard-codes "A is always old" passes a naive test and fails this one.
- Bijection: every label maps to exactly one version, every expected output is claimed exactly once. No duplicates, no orphans.
- Ordering independence: shuffle the input rows; the mapping output must be identical.

**Completeness**
- Count assertion: 12 items x 2 versions = 24 mapped rows. Fail loudly on 23 or 25.
- A judgement whose label is not in the key raises an error rather than being dropped, defaulted, or silently binned under one version.
- A key entry with no corresponding judgement is reported as missing, not ignored.

**Malformed and adversarial input**
- Label case/whitespace variants ("a", "A ", "Answer A") — either normalised deliberately and tested, or rejected. Not both.
- Duplicate labels within one item.
- Empty file, header-only file, truncated last row.
- A judgement referencing an item_id that does not exist.
- Corrupted or edited key file: if the key carries a checksum or seed, verify it; a key that no longer matches the run must abort the tally.

**Sequencing / leakage**
- The script refuses to run, or the pipeline refuses to accept its output, if the judging outputs are not complete and frozen. Unblinding early is the way this whole exercise gets compromised, and the test is: given an in-progress judgement file, assert the script errors.
- Assert the script writes nothing back into the judging inputs, and that the key file is not readable from the judge's working directory (a path/permission test, if the layout allows it).
- Assert the blinded artefacts contain no version identifier — a grep-style assertion over the anonymised outputs for the version names, model IDs, and filenames.

**Idempotency and determinism**
- Running twice produces byte-identical output.
- Same seed reproduces the same blinding; a different seed produces a different one (otherwise the randomisation is not actually happening).

**Tally-level sanity**
- A golden fixture with a known, planted result — e.g. new wins 8, old wins 2, 2 ties — asserting the tallied numbers exactly. This catches an off-by-one in the join that per-row tests miss.
- A fixture where the mapping is deliberately inverted must produce the mirrored tally; if it does not, the tally is not actually reading the mapping.

## Q3

No — that sentence cannot be the headline, and as written it may not mean anything.

"Answer A" is a **position label**, not a version. If the pairing was randomised per item (it should have been), there is no single thing called "answer A" across the set — A was the old version on some tickets and the new one on others. A statement averaged over that is meaningless, and quoting it as the headline would report position bias as a product finding.

Two possibilities, and they need separating before anything is written:
1. The judge was given a fixed order for the whole set, in which case "A" does identify a version — but then the result is confounded with position bias and is weak evidence, not headline material.
2. The order varied per item, in which case the sentence is an artefact of the judge summarising across items it saw in different arrangements, and should be discarded outright.

What I would do instead: ignore the judge's own closing summary entirely — it is a free-text flourish written without access to the aggregate — and compute the headline from the per-item structured judgements after un-blinding. Then the headline names the version, states the margin, states n=12, and states the tie/flip rate.

If someone wants a sentence today: "Across 12 tickets the [version] won X, lost Y, tied Z; the difference is/is not larger than the judge's own order-to-order disagreement." That is a headline that survives being checked.

## Q4

No. Telling a judge to ignore position does not make it ignore position.

Position bias in pairwise LLM judging is a property of how the model processes the two candidates, not a stated intention it can decide to set aside; instructing it to be unbiased reliably changes what it *says* about its reasoning and not much about which one it picks. You also lose your only means of detecting the problem: with a fixed order there is no measurement that distinguishes "A was better" from "A was first".

The instruction costs nothing, so keep it — but it is not a substitute. The thing that actually works is mechanical and cheap:
- Randomise the slot assignment per item (one line: seed + shuffle).
- Run each pair in both orders and average, or count a disagreement between the two orders as a tie.
- Report the slot-A win rate as a diagnostic. If it sits near 50%, you have evidence the arrangement did not drive the result; if it does not, you have found the bug rather than shipping it.

The swap doubles judge calls. On 12 items that is 12 extra calls — far cheaper than a wrong decision about the summariser prompt, and far cheaper than re-running the comparison in a month when someone asks whether the order mattered.

## Q5

No — that reasoning is inverted. Closeness is the argument *for* blinding, not against it.

Blinding matters in proportion to how small the true difference is. When one candidate is obviously better, a biased procedure still lands on the right answer and the sloppiness is harmless. When the candidates are near-identical, the real signal is small enough that position bias, formatting tells, and the expectation that the new version should win are all comfortably large enough to decide the outcome on their own. An unblinded close comparison does not produce a weak answer; it produces a confident answer generated by the bias.

There is also a second cost: "they're very close" is itself an unmeasured prior. If it is right, the honest result is likely "no detectable difference at this sample size", which is a genuinely useful finding — and one only a clean procedure can deliver. An unblinded run cannot report it, because it will always find a winner.

Blinding here is a shuffle, a key file, and a join. Keep it. If something has to be cut for time, cut the sample size or the number of criteria, not the blinding — those degrade precision, this one degrades validity.
