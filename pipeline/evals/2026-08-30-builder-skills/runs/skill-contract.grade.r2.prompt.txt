QUESTION 2
Draft the steps section for a skill about reviewing database migrations. You have a probe transcript showing two observed failures.

EXPECTATIONS:
  - each rule names the observation behind it
  - no rule is included that the probe did not show failing
  - every step ends in something checkable

--- ANSWER A ---
I would anchor every step to the probe transcript and nothing else. Two observed failures means two steps that are guaranteed to earn their place: each one exists because the probe showed the behaviour is missing without it, and I would write each step in the imperative with the concrete check that would have caught the observed failure (for migrations, typically things like "confirm the migration is reversible or state explicitly that it is not" and "check the table's row count and whether the change takes a blocking lock on it"). Around those I add only the minimum scaffolding needed for the steps to be executable — what to read first, what to output. I would not pad the section with the generic migration-review checklist I could write from memory; unearned steps dilute the two that are evidence-backed and make the skill longer to load for no measured gain. I would mark in my handoff which steps are backed by an observed failure and which are speculative, and I would say plainly that two probes is a thin evidence base: before shipping I would run more probes to find the failures the transcript did not surface, and let those add steps.

--- ANSWER B ---
Two observed failures means exactly two rules. I'd open the probe transcript, quote the two failures verbatim, and write one step per quote — each named with the run it came from, each ending in something checkable: a file and line in the migration, a named artefact (the rollback script, the lock-timeout setting), a number, or a table row. Anything else that wants into a migration-review steps section — index-build locking, backfill batch size, "consider whether the change is backwards compatible" — stays out unless the probe actually showed it failing. That advice is free to write and expensive to carry: it costs context on every invocation and cannot be measured, because nothing was failing without it. The test is mechanical — name the run, or it doesn't go in. If two rules feel thin, the answer is more probing, not more opinions. Then the code checker on the whole file, then the reader's question: is every rule traceable to a named observation, and does every step end in something checkable?

QUESTION 4
Two skills in this library both mention reviewing schema changes. Write the new one's description.

EXPECTATIONS:
  - reads the sibling's description before writing
  - states which unit owns which job, from both sides

--- ANSWER A ---
I wouldn't write it yet — the description is written last for a reason, and it needs three inputs. First the new skill's finished body, so the scope has stopped moving; second the trigger vocabulary, the words someone types while having the problem rather than the words for the fix; third the existing skill's description in full, verbatim, since that is the thing I must not collide with. So: read the sibling's description, list what it actually owns, and write the new one around what the sibling does not do, in symptom language.

Then the mutual router test, and it runs in both directions. Take the sibling's job as a user would type it and ask which of the two a router picks and why not this one; take the new skill's job and do the same. If either answer is unclear, one of the two descriptions is wrong — and often it's the older one, so I'd expect to edit both and re-run the checker on each. I'd also add the explicit negative to the new description (the sibling's job named, and where it goes instead), because a boundary asserted from only one end fails from the other.

--- ANSWER B ---
I would not write it from the two names alone — I would read both skills' bodies first and find the discriminator: the thing that is true of one job and false of the other (for example, one reviews a migration diff before it runs, the other reviews the resulting schema design). The new description then leads with its own triggers in that narrower language, and ends with an explicit negative clause naming the sibling by name: "NOT for <the sibling's job> (use <sibling>)." And I would edit the sibling's description in the same change to point back the other way. A boundary asserted from only one end is not a boundary — the sibling keeps claiming the overlap and the collision persists. After both are written I test it: a handful of requests phrased the way a user would phrase them, confirming each routes to the intended skill and that each fires on none of the other's cases.
