## Q1

I would not work in "whatever order I think best" — I would work in a fixed order, because the order is what keeps the contract honest. First I read the field contract itself and list every required field and its constraint (name pattern, description length cap, allowed frontmatter keys), so I am checking against the actual text and not my memory of it. Second I write the BODY of the skill — the method, the steps, the failure modes — because the description has to describe what the skill actually does, and if I write the description first the body drifts to match the sentence. Third I derive the description from the finished body: third person, triggers-only ("Use when..."), keyword-rich, plus explicit negative triggers naming the sibling skills a request should go to instead. The candidate sentence I treat as a hypothesis about the trigger surface, not as the description — I keep it only if the finished body earns it. Fourth I go field by field down the contract and verify each one against the file, measuring the description's character count rather than eyeballing it. One flag: the contract and the candidate sentence are not attached to this question. I would ask for both and read the contract file rather than write a SKILL.md against a remembered shape of it.

## Q2

I would anchor every step to the probe transcript and nothing else. Two observed failures means two steps that are guaranteed to earn their place: each one exists because the probe showed the behaviour is missing without it, and I would write each step in the imperative with the concrete check that would have caught the observed failure (for migrations, typically things like "confirm the migration is reversible or state explicitly that it is not" and "check the table's row count and whether the change takes a blocking lock on it"). Around those I add only the minimum scaffolding needed for the steps to be executable — what to read first, what to output. I would not pad the section with the generic migration-review checklist I could write from memory; unearned steps dilute the two that are evidence-backed and make the skill longer to load for no measured gain. I would mark in my handoff which steps are backed by an observed failure and which are speculative, and I would say plainly that two probes is a thin evidence base: before shipping I would run more probes to find the failures the transcript did not surface, and let those add steps.

## Q3

No. "Reads well" is not the criterion — the description has a hard budget, and 1,380 characters is over the 1,024-character cap the skill listing enforces, so it gets truncated or rejected and the tail of the description (usually where the negative triggers live) is exactly what disappears. I would cut it to triggers-only: delete any sentence that explains how the skill works, what it produces, or why it is good, since none of that participates in selection; keep the "Use when..." trigger phrases, the distinctive keywords a user would actually type, and the NOT-for clauses naming the sibling skills. Then I measure the result rather than estimating it, and re-check that the trimmed version still fires on the trigger cases and stays silent on the negative ones.

## Q4

I would not write it from the two names alone — I would read both skills' bodies first and find the discriminator: the thing that is true of one job and false of the other (for example, one reviews a migration diff before it runs, the other reviews the resulting schema design). The new description then leads with its own triggers in that narrower language, and ends with an explicit negative clause naming the sibling by name: "NOT for <the sibling's job> (use <sibling>)." And I would edit the sibling's description in the same change to point back the other way. A boundary asserted from only one end is not a boundary — the sibling keeps claiming the overlap and the collision persists. After both are written I test it: a handful of requests phrased the way a user would phrase them, confirming each routes to the intended skill and that each fires on none of the other's cases.

A confident summary of a contract is indistinguishable from a correct one until something downstream fails the check, and by then it has been built on.
